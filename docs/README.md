# Documentation Index

This documentation is organized by **domain**, not as a flat list of files. Each domain owns the decisions and knowledge specific to its area of the project. Documents are created as empty, professionally structured templates first, and filled in deliberately as decisions are made.

## Domains

| Domain | Purpose |
|---|---|
| [`product/`](product) | What the product is, who it's for, why it exists, and how it evolves |
| [`branding/`](branding) | The brand's identity, visual assets, and voice |
| [`design/`](design) | The design system and UX/UI principles that implement the brand |
| [`technical/`](technical) | The engineering architecture that powers the product |
| [`seo/`](seo) | The strategy for organic visibility across target markets and languages |
| [`development/`](development) | The conventions and processes the engineering team follows |

## Document Status

Templates in this documentation set start as headings-only skeletons. As each document is authored, it should carry a status so contributors know what's authoritative:

- `Draft` — structure in place, content being written
- `In Review` — content complete, pending Product Owner validation
- `Approved` — validated and authoritative

## Conventions

- One document, one concern. Prefer splitting a document over letting it sprawl.
- New documents belong in the domain folder they most relate to; add them to the relevant section below once created.
- Cross-domain references should link to the specific document rather than duplicate its content.
